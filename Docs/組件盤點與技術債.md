# 組件盤點與技術債（2026.11.14）

**一句話**：Windows 版的本體是 SRS 7 + 自製 POSIX 相容層 + 自製 st-srs Windows 移植；目前結構性風險集中在「事件迴圈、行程／訊號、相容層重複、建置與測試雙軌」。

這份文件只記錄**現況與判斷**，不是修改計畫；決策確認後再更新 `TODO.md`。

## 1. 目前實際使用的組件

### 1.1 伺服器本體（`trunk/src`）

| 模組 | 角色 | Windows 現況 |
|------|------|--------------|
| `core` | 平台偵測、日誌、錯誤、時間、記憶體 | 可編譯；大量 `_WIN32` 分支 |
| `kernel` | RTMP／FLV／TS／MP4／PS、buffer、codec、 utility | 可編譯 |
| `protocol` | RTMP、HTTP（llhttp）、ST、AMF0、RTP／RTCP、SRT | 可編譯；SRT 取決於外部依賴 |
| `app` | server、listener、HTTP API／HLS／DVR、edge、RTC、GB28181 | 可編譯；RTC／SRT 預設關閉 |
| `main` | 啟動、daemon、pid | 可編譯；Windows 無 daemon |
| `utest` | 36 個測試檔 | **未建置、未執行**（CMake 沒有 utest target） |

### 1.2 第三方元件（`trunk/3rdparty`）

| 元件 | 版本／來源 | 用途 | Windows 實際使用 | 風險 |
|------|------------|------|------------------|------|

| `openssl-1.1-fit` | OpenSSL 1.1.x | vendored SSL | 否（用系統 OpenSSL） | 老版本；與系統 3／4 並存 |
| `ffmpeg-4-fit` | FFmpeg 4.x | 內部轉碼 | 否（用 stub） | 老版本；功能不可用 |
| `srt-1-fit` | SRT 1.x | SRT 協議 | 否（預設未啟用） | 需 vcpkg 才啟用 |
| `gperftools-2-fit`／`gprof` | gperftools 2.x | profiling | 否 | 未使用 |

### 1.3 相容層：實際上有三套重疊

| 層 | 檔案 | 狀態 |
|----|------|------|
| 強制引入層 | `trunk/ide/srs_msvc/force_include.h`（547 行） | **真正生效**（`/FI`）；型別、POSIX 映射、stub、`FD_SETSIZE=8192` |
| 另一套包裝 | `trunk/ide/srs_msvc/srs_win32_compat.h`（264 行） | **沒有被任何原始碼 include**，只在 CMake include path 中；死碼／重複 |
| 偽 POSIX 標頭 | `trunk/ide/srs_msvc/compat/`（21 個標頭） | `epoll`／`inotify`／`mman`／`wait`／`dlfcn`… 多為 `ENOSYS` stub |

問題：同一語義在不同檔案有多份定義，行為不一致。例如 `pipe()` 是 CRT `_pipe()`，但 st-srs 對所有 fd 都用 `recv()` 讀；`srs_socketpair()` 已存在卻沒有人用。訊號 pipe 空轉就是這個落差的結果。

## 2. 功能現況 vs 文件宣稱

| 功能 | README 宣稱 | 實際 Windows build（預設） | 證據 |
|------|-------------|----------------------------|------|
| RTMP | ✅ | ✅（事件迴圈修正後） | 本機 handshake 16 bytes |
| HTTP-FLV／TS／HLS | ✅ | 需逐一驗證 | HTTP server 已回應 |
| WebRTC（WHIP／WHEP） | ✅ | **❌ 預設關閉**（缺 libsrtp／opus，`SRS_AUTO_RTC` 未定義） | CMake configure `RTC=FALSE` |
| SRT | ✅ | **❌ 預設關閉**（`SRT not found`） | CMake configure `SRT=FALSE` |
| GB28181 | ✅ | 巨集有定義；UDP／媒體路徑未驗證 | `srs_auto_headers.hpp` |
| DVR | ✅ | 需驗證 | — |
| 內部轉碼 | — | **❌ FFmpeg stub**（`avcodec_open2` 回 -1） | `ffmpeg_stubs.c` |
| daemon | — | ❌ foreground only | `run_directly_or_daemon()` |
| 設定 hot-reload | — | ❌ inotify stub | `force_include.h` |

> README 的功能表目前是「上游 SRS 的能力」，不是「這個 Windows build 的預設能力」。这是文件與產物不一致的根源。

## 3. 過時或需要重新設計的元件（依風險排序）

### P0：已造成事故或會再造成事故

1. **st-srs Windows 移植**
   - 自製 context switch（`md_win64.asm`）、`select()`、TLS、stack 管理。
   - 本週已修：`MD_GET_SP` 用 32-bit `long` 索引 64-bit context、idle thread 64KB stack 放不下三份 64KB `fd_set`、signal pipe 空轉。
   - 缺回歸測試；任何一個小改動都可能再次讓 listener 不接受連線。
   - **建議**：短期補 context／stack／select／多 listener 的回歸測試；中期評估 libuv／Boost.Asio／執行緒池／IOCP，替換整個協程層。

2. **`select()` + `FD_SETSIZE=8192`**
   - `_st_select_dispatch` 在 stack 上放三份 `fd_set`，每份約 64KB；O(n) 掃描。
   - 已用 256KB idle stack 暫時避開溢位，但不是可持續設計。
   - **建議**：改用 `WSAPoll`（較平滑）或 IOCP（長期）；至少把「FD_SETSIZE × 3 的 stack 需求」做成編譯期檢查。

3. **PID 檔沒有真正鎖定**
   - `SrsPidFileLocker::acquire()` 用 `open()`（無 `O_EXCL`）＋`fcntl(F_SETLK)`；Windows 的 `srs_fcntl` 對 `F_SETLK` **直接回 0**（no-op）。
   - 所以舊 `srs.pid` 不會阻止啟動，1034 只是「open 失敗（`objs` 不存在）」的包裝錯誤。
   - **建議**：`LockFileEx` 或 named mutex；明確區分「權限不足／路徑不存在／已在執行」。

4. **POSIX stub 靜默降級**
   - `fork()`、`kill()`、`waitpid()`、`inotify_*()`、`mmap()`、`flock()` 等回 `ENOSYS` 或 no-op；呼叫端常忽略回傳值。
   - 結果是「功能看起來存在、實際不做」；訊號 pipe 與 pid 鎖都是同類問題。
   - **建議**：stub 一律回傳明確錯誤並在啟動時列出「Windows 不支援」清單；功能用 build flag 明確 gate，不要靠執行期失敗。

### P1：結構與可維護性

5. **三套相容層重疊**：刪除未使用的 `srs_win32_compat.h` 或合併進 `force_include.h`；`compat/` 只保留真正被 include 的標頭。

6. **建置雙軌**：CMake 與 Linux `configure` 各自生成 feature headers；Windows 的 `srs_auto_headers.hpp` 硬編碼日期與空 TS。建議由 CMake 從 git／時間生成，或共用同一套 header 產生器。

7. **Docker／Linux dev lane 不可重現**：Windows checkout 的 CRLF 讓 vendored `libsrtp-2-fit/configure` 出現 `/bin/sh^M`；`dos2unix` 對該檔**靜默跳過**（被判定為 binary），所以需要 `sed -i 's/\r$//'` 或改用系統 libsrtp。`.gitattributes` 目前只涵蓋 `*.c`／`*.h`／`*.sh`，沒有 `configure`。

8. **依賴版本政策**：libsrtp 2.3.0、FFmpeg 4、OpenSSL 1.1-fit、SRT 1、gperftools 2；系統 OpenSSL 3／4 與 vendored 1.1 並存。需要一份「支援矩陣 + 升級節奏」。

9. **測試缺口**：utest 未跑、smoke 只驗 HTTP、沒有 RTMP／併發／關閉流程測試。本週的事件迴圈 bug 就是因為只驗 HTTP 而漏掉。

### P2：文件與交付

10. **文件漂移**：`Windows移植技術文件.md` 的檔案行數、輸出清單（`srtp2.dll`、`srt.dll`、`live.conf`）與實際不符；README 功能表與 build flags 不一致。
11. **Artifact CRT**：nightly 是 Debug，需要 `*D.dll`（不可轉散布）；Release 才是一般使用者可跑的版本。建議 nightly 也產 Release，或明確標示 Debug 仅开发机。
12. **開發環境**：本次新增 `dev/`（Windows `srs-dev.exe`＋Docker lane），但 Docker lane 尚未打通（上述 CRLF）。

## 7. 下一步（依決策）

1. **Windows RTC／SRT**：需要 MSVC 可用的 libsrtp（vcpkg `srtp` 或升級到 2.6 的 CMake）與 SRT（vcpkg 或 vendored 1.5.3 CMake）。這是「正式支援」的唯一缺口。
2. **FFmpeg**：Windows 目前只有 stub；要真正支援轉碼／RTC 音訊，需要 FFmpeg 7.x（vcpkg／預編譯）或明確改為外部 `ffmpeg.exe`。
3. **OpenSSL**：移除 vendored 1.1.1l，CI 與本機一律使用 OpenSSL 3.x；同步淘汰 `compat/openssl/compat.h` 的舊 API 映射。
4. **清理**：依上表移除 dead 元件，並同步 `depends.sh`／`copy_to_gits.sh`／`copy-srs-docs.sh` 的參照。
5. **測試**：把 `st-event-loop-test` 與 RTMP handshake 納入 nightly；恢復 `utest` 與 Linux 回歸測試。
